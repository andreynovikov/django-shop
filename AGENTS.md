# sewing-world.ru storefront (cartzilla)

Next.js storefront for sewing-world.ru (package name `sworld`, branch `sworld`), styled with Tailwind CSS v4 after the look of the Cartzilla theme it was built on. It has no database of its own: all data comes from a separate Django backend (the `django-shop` repo, checked out in `../django-shop`) over REST at `${API_SERVER}/api/v0/`. The UI and content are in Russian; code comments are in English.

- This file is the project's only instruction file. `CLAUDE.md` just imports it and `tests/AGENTS.md` for Claude Code, so put guidance here, never there. Read [tests/AGENTS.md](tests/AGENTS.md) before running or changing tests.
- Keep reusable development preferences out of this file (`~/.codex/AGENTS.md`, `~/.claude/CLAUDE.md`). Prefer current code and configuration over historical rollout notes.

## Commands and configuration

- Use npm and `package-lock.json`; install dependencies with `npm ci`.
- `npm run dev`: plain `next dev` at http://127.0.0.1:4004 (no HTTPS since 2026-11-23). Playwright reuses it when it is already running, otherwise starts it.
- `npm run build` / `npm start`: production build (`output: 'standalone'`) and server on port 4004.
- `npm run lint`: ESLint over `src/` (next core-web-vitals, next typescript, and the tanstack-query recommended rules). There is no separate formatter.
- Type check: `npx next typegen` (writes the route types `PageProps`/`LayoutProps`), then `npx tsc --noEmit`. For code changes run lint, typegen and tsc in that order, as CI does, and not at the same time as Playwright.
- `npm run test:e2e`: Playwright tests in `tests/` (chromium, firefox, webkit, Mobile Chrome, Mobile Safari). One file: `npx playwright test tests/checkout.spec.ts`; one test: `-g "anonymous buyer orders"`; one browser: `--project=chromium`. Local runs go against a local Django, and tests never write to a real backend; see `tests/AGENTS.md`.
- Environment: `API_SERVER` (host only), `API_TOKEN`, `FRONTEND_KEY` (the site's key from its profile in Django) and `REVALIDATION_TOKEN` (used by `/api/revalidate`) are server-only; the browser gets `NEXT_PUBLIC_YMAPS_API_KEY` and the `NEXT_PUBLIC_*_VERIFICATION` values. `ORIGIN` is obsolete.
- `.env` names production. For local builds and API investigation, set `API_SERVER=http://127.0.0.1:8000` (a django-shop runserver) on the command line; a variable already set wins over `.env`. Keep the local site profile's existing frontend key (it equals `.env`'s `FRONTEND_KEY`); don't overwrite it.

## Architecture

Stack: Next.js App Router, React, TypeScript, TanStack Query, nuqs, Tailwind CSS v4, Base UI and Tabler icons. Read the installed Next.js docs before code changes (managed block at the end).

### App Router
Everything is in `src/app/`. The route groups `(auth)` (login, registration), `(pages)` (service centers, stores, warranty) and `(shop)` (catalog, products, search, cart, compare, checkout) only sort the files. Beside them are `user/` (account pages, noindex via `user/layout.tsx`), `blog/`, `actions/`, `pages/[...uri]` (content pages), `oldforum/`, `sitemap.ts`, the API proxy, `api/revalidate` and the XML feeds.
- The root `layout.tsx` loads the catalog and renders the topbar, bottom bar and handheld toolbar around every page. `providers.tsx` sets up TanStack Query, nuqs, the site, navigation, the session, toasts, and the topbar and toolbar contexts.
- Page headers come from the hook-free `pageContentWrapper()` (`src/components/layout/page-content-wrapper.tsx`), so server components can render them. It combines `PageHeader` (the frame) and `PageTitle` (breadcrumbs and `h1`), which a layout can also use separately.
- Account pages share `user/layout.tsx`, which holds the header frame and the sidebar. Each page's title, breadcrumbs and metadata are in the `@header` slot, in a page at the same path (`user/@header/orders/[id]/page.tsx` next to `user/orders/[id]/page.tsx`), so a new account page needs both files. The sidebar stays mounted between account pages, so its state carries over.
- User data (session, basket, favorites, comparisons, orders) is loaded in the browser only, so the pages that show it stay static. Never move personalized state into server-rendered output. Components that read the query (`/search`, `/compare`, `/user/orders`, category filters) use nuqs inside a Suspense boundary: the route's `loading.tsx`, or a `<Suspense>` around the component when the header must stay out of the fallback. A header that should show while a page loads goes in the segment's `layout.tsx`, outside the `loading.tsx` boundary (see `/products/[code]`, `/compare`).
- Client components use `next/navigation` directly: `useRouter()` to navigate and `usePathname()` for the path. `useSearchParams()` (and nuqs) needs a Suspense boundary in static routes. Keep each boundary around just the part that renders from the query, with a fallback that renders it without the query, so the rest of the page stays in the static HTML (see `RegisterLink` in `login-form.tsx` and `CurrentCatalog`). Event handlers read the URL from `window.location` instead of a hook.

### Data layer (`src/lib/queries/`)
- Each resource module exports a query-key factory (`xxxKeys`) and plain `load*`/`retrieve*` functions built on `apiFetch` (`fetch.ts`). Loaders that static pages use pass the request's cache tags with `tagged(...)`, see "Static generation and revalidation". Everything is re-exported from `@/lib/queries`.
- `apiFetch` sends requests with a body to the relative `/api/v0/...` path. That path is the proxy `src/app/api/v0/[...path]/route.ts`, which forwards cookies, sets Django's `X-CSRFToken` header from the `__Host-csrftoken` cookie, and passes `Set-Cookie` back. Requests without a body are prefixed with `API_SERVER`. `API_SERVER` isn't `NEXT_PUBLIC_`, so it is set only on the server. As a result, server-side GETs go straight to Django, and every browser request goes through the proxy. The proxy exports only GET, POST and PUT.
- Server-side requests and the proxy send `X-Frontend-Key: FRONTEND_KEY`, and the proxy passes on `X-Real-IP` from nginx. With the key, Django takes the site from it and the client address from `X-Real-IP`. Without one, Django ignores the session cookie, refuses writes that have no token, and uses the default site, so the build needs the key too. sewing-world.ru is the default site, so with a wrong key its reads still look right; only sessions and writes fail.
- The proxy's safeguards are deliberate, keep them: it forwards only the request headers in `REQUEST_HEADERS` (the browser's `Origin` included, which Django's CSRF check needs); a POST or PUT needs `X-Requested-With` and an absent or `same-origin` `Sec-Fetch-Site`, which `apiFetch` satisfies (copying the CSRF cookie into a header alone protects nothing); dot segments and slashes in path segments are refused; redirects are passed back, not followed; `users/logout` is POST only; and `content-encoding`/`content-length` are dropped from the answer, because fetch has already decoded the body (passing them on broke every API call when nginx turned on brotli). `CSRF_COOKIES` still lists the old `csrftoken` name until the cookie-rename transition ends, see "Known follow-ups".
- Placing an order (`useCreateOrder` in `lib/order.ts`) sends the basket id as `Idempotency-Key`, which the proxy forwards for `POST orders/` only, and retries once after a network error or a 5xx. Django answers a repeat with the order the key already made, so a lost answer never orders twice; Metrika's purchase event is sent once per order id. Keep the key, the forwarding and the single retry together.
- `API_TOKEN` (`queries/tokenized.ts`, for the XML feeds) and `FRONTEND_KEY` are used only in server code.
- `userReferences` and `userDependencies` in `queries/index.ts` list the queries that are reset when the user changes (login, logout, another user in another tab) and invalidated whenever the user is loaded. Update them when you add user-specific queries. A failed logout must be reported to the user.
- `src/lib/query-client.ts` sets the default `staleTime` to 60 s; categories and pages never go stale, products stay fresh for 10 minutes. Because of the default, `initialData` counts as fresh and the query is not fetched for a minute, even when it becomes enabled later. For a list that is empty until loaded, use a module-level empty constant as the destructuring default instead (see `useComparison` and `useFavorites`).
- Shared types are in `src/lib/types.ts`. Cross-cutting hooks and contexts are in `src/lib/`: `useSite`, `useSession`, `useBasket`, favorites, comparison, topbar/toolbar.
- Django leaves out null, empty-string and empty-list fields, so a field can be missing even where a type says it is required; guard lists such as product images with `?? []`. `products/?ta=1` returns title strings. An empty `ordering=` keeps the backend's relevance order; `variations=` means no variations.
- Product filters are objects serialized with `productSearchParams`, not `{field, value}[]` arrays. Keep the backend's filter metadata contract (`class`, `widget`, `choices`, `attrs.step/min_value/max_value`). `fields=` limits what an API read returns; it is not catalog URL state.
- The price filter and sorting use `cost` (the shown price, discounts included). Keep `price` in the API contract and the sitemap/XML bounds `price: [0, 10000000]`. Search uses Diginetica, not the backend; keep it out of backend filter changes.

### Static generation and revalidation
- Pages are cached with fetch tags; this is not a Cache Components setup, and moving to one was never planned.
- `generateStaticParams` pre-renders every entity only when `NODE_ENV === 'production'` and `PLAYWRIGHT_TEST !== 'true'`; otherwise it returns `[]`, and each page is rendered on its first request and cached. CI sets `PLAYWRIGHT_TEST=true` so the build stays fast. Follow the same guard in new static routes.
- Pages are revalidated by tag. Each loader in `lib/queries` tags its request with the data it asks for (`lib/queries/cache-tags.ts`: `catalog`, `category:<id>`, `product:<code>`, `action:<slug>`, …), and a static page gets the tags of every request it makes, even though the requests themselves aren't cached. When data changes, django-shop (`shop/revalidation.py`) works out the tags the change touches and POSTs `{ secret, tags, background? }` to `/api/revalidate` (`src/app/api/revalidate/route.ts`) with `REVALIDATION_TOKEN` as the secret; the handler calls `revalidateTag()`, at once (`{ expire: 0 }`, the next visit waits for the render) or with `background: true` as stale-while-revalidate (`'max'`). The old `{model, pk}` payload is gone. The two lists of tags must match: a new loader used by a static page needs a tag here and the change that touches it a tag there.
- Admin edits and price changes expire pages at once. Stock changes revalidate in the background, and only when the availability shown changes (0 / 1 / >1 / >5 / whole pack); the 1C import is compared before and after and sent in one batch, never one product at a time.
- Lists of the whole catalog (sitemap, feeds) are not tagged by product, see `productListTags()`.
- The time-based `revalidate` catches what the signals miss: an hour for the home page, the catalog and products, a day for the rest (actions, stores, service centers, content pages, sitemap); the feeds stay hourly and the old forum is static. `/pages/[...uri]` renders pages added after the build on their first visit.
- Staff open `/api/revalidate/?path=/catalog/sewing/` (or `?all` for every page) while signed in on the storefront: the route asks Django for the session's user (`is_staff`), revalidates the page and redirects to it (303), and answers 403 to anyone else. Next keeps pages by their route files, so only one page or the whole site can be asked for.
- `next dev` doesn't cache pages; check caching on a production build (`tests/AGENTS.md` has the steps).

### XML feeds
`src/app/xml/[filename]/route.ts` serves product feeds such as `/xml/market.xml`. It renders the EJS templates in `templates/xml/`. `products` and `search` are global feeds. Any other filename is treated as an integration UTM, looked up on the backend, and rendered with that integration's `output_template`. In Docker, `templates/` is mounted as a volume from the server's site directory, so SEO can edit the templates without a new build; only this branch keeps copies in the repository. For that reason the build renders no feed (`generateStaticParams` returns `[]`, without the usual production guard): a feed rendered at build time would be baked into the image from the repository's templates, or as a 404 where there are none, and served for an hour after each deploy. Each feed is rendered on its first request and then cached like the other pages.

### Styling
- Tailwind CSS v4 through `@tailwindcss/postcss`. `src/styles.css` holds the theme: Cartzilla's colors and grays, the `text-h1`–`text-h6` heading sizes, `text-ms`/`text-md`, radii, shadows and the `container`. It scans only `src/` (`source('.')`). The base layer adds link and heading colors, inline Tabler icons and `.sw-shown-md`/`.sw-shown-lg` for `keepMounted` Collapsible panels that stay shown from a breakpoint up, which preflight's `[hidden]` would hide. Collapsible panels with crawlable links stay mounted.
- Breakpoints are Tailwind's defaults; `lib/breakpoint.ts` has the same values.
- Components use utilities inline. Repeated Cartzilla patterns are class helpers in `src/components/ui/`: `buttonClass`, the form classes, `Alert`, `badgeClass`, card, menu, nav, widget, navbar tool and handheld toolbar classes, `carouselNavClass`, slider classes, and the Base UI wrappers (modal, offcanvas, tooltip, autocomplete). New UI parts use named exports. There is no tailwind-merge: don't add a class that sets what a helper already sets (e.g. a second `px-*` or display), add a helper option instead.
- Icons are Tabler (`@tabler/icons-react`), usually `stroke={1.5}`.
- Base UI Autocomplete adds a hidden input, so a form without a submit button no longer submits on Enter; the mobile search keeps a visually hidden submit button for that.
- Swiper's CSS is unlayered, so display utilities on slides and on the Swiper root need `!`. Keep the space reserved for its pagination: a layout shift between pointerdown and pointerup closes a Base UI menu (seen in Mobile Safari).
- HTML from the backend (product texts, pages, blog, actions, stores) goes into `contentClass()` from `ui/content.ts`: the typography plugin's `prose`, tuned to Cartzilla's spacing. Adverts get `advertClass`.
- The stored HTML still has Bootstrap classes. `src/backend-content.css` styles the ones it uses, scoped to `.backend-content`, until django-shop's `manage.py tailwindize_html --write` converts them; then delete it and remove `backend-content` from the content classes (see `shop/tailwind_html.py` in django-shop). `src/backend-safelist.css`, printed by that command and identical in every storefront, makes Tailwind generate the classes of the converted HTML. The command is a dry run by default: never run `--write` on the local `sworld` database; try it on a copy, keep classes that a `<style>` inside the HTML uses, and check that a second pass changes nothing.
- The Playwright tests select by role, label and text, so icon-only controls need accessible labels.

### Shared with the other storefronts
The storefronts are copies, not a shared package. janome.club, singer.ru and dor-tak.ru copy some files from here unchanged, so a change made here is copied to them:
- `src/lib/` (familysew.ru copies it too);
- `app/api/revalidate/route.ts` and the proxy `app/api/v0/[...path]/route.ts` (familysew.ru too);
- the XML feed route, where a storefront has feeds;
- the container files `startup.sh`, `container-entrypoint.sh` and `src/instrumentation.ts`, the `Dockerfile` apart from its `entity`, and `.dockerignore` (familysew.ru too);
- the user-flow components (familysew.ru has no login and doesn't have them):
  - `components/user/`: login, registration, update and confirm-email forms, `phone-code-input`, `profile`, `sidebar`, `topbar`, `avatar`;
  - `components/order/`: `confirmation`, `details`, `list`, `payment-button`, `status-badge`;
  - `components/cart/contents.tsx` and `item.tsx`, `components/countdown.tsx`, `components/product/product-link.tsx`.

Shared dependencies get this storefront's versions when syncing.

Each storefront keeps its own versions of the rest:
- `src/storefront.ts`, which the shared code reads: whether there is a favorites page, whether products have pages (otherwise `ProductLink` renders no link), and the backend filters of the products the site lists (`baseFilters` in `lib/catalog`, e.g. `show_on_sw` here). What the backend knows about the site comes from `useSite()` instead, such as `wholesale` (whole packs in the cart). Orders are filtered by site everywhere.
- The `components/ui/` helpers the shared components use: `form`, `button`, `alert`, `badge`, `nav`, `widget`, `tooltip`. They have cartzilla's API with the storefront's own classes.
- Theme tokens in `styles.css`:
  - `text-h1`–`text-h6`, `text-ms`, `text-md`, `text-heading`, `text-link-hover`;
  - `text-overlap` and `pb-overlap` for content pulled up over an overlapped page header: white and 3rem here, the body color and 1rem where the page header doesn't overlap.
- The header cart (`cart/notice.tsx`) and the pages in `app/`.

A shared component styles itself only through these helpers and tokens, never with branches for a brand. When it needs a new helper option or token, add it to every storefront.

## Release and deploy
- The storefronts are branches of the django-shop GitHub repository; its `main` is the backend.
- `.github/workflows/frontend.yml` runs on every push to `sworld`:
  - lint and type checks, then the Playwright tests and the Docker build side by side;
  - the image goes to `ghcr.io/andreynovikov/sworld`, tagged `latest` and with the commit's Moscow date and short hash, e.g. `2026.11.11-7f57710`;
  - then it is deployed to stage on port 4004. Stage waits for the build only, not for the tests.
- Production (port 4104) is deployed by hand: Actions → Frontend CI → Run workflow on the `sworld` branch. That deploys the image of the branch's head commit without rebuilding it. Re-running an earlier deploy run rolls back. There are no version numbers or release tags. A green build is not permission to deploy production.
- The image holds no configuration. The build and the tests take `ENV_FILE` from the `sworld` GitHub environment: the Docker build gets it as a BuildKit secret, mounted as `.env.local` for `npm run build` only (Next copies `.env` into `.next/standalone`, but not `.env.local`), and `.dockerignore` keeps every `.env*` out of the context. At runtime, the server's `.env.storefront` in the deployment directory is mounted as `/app/.env.local` by the shared Compose file, and `startup.sh` refuses to start without it. Stage runs the production image with its own copy. A changed server-only value (`API_SERVER`, `API_TOKEN`, `FRONTEND_KEY`, `REVALIDATION_TOKEN`) needs the server file changed and the container recreated (`docker restart` may keep a replaced file); a `NEXT_PUBLIC_*` value, or anything the build renders pages from, needs a new build too. Keep `ENV_FILE` and the server files the same. "Storefront configuration" in `deploy/README.md` on `main` has the steps.
- A deploy job logs in over ssh (`DEPLOY_USER@DEPLOY_HOST` with `SSH_PRIVATE_KEY`, the host key pinned by `DEPLOY_HOST_KEY`; keep the pinning) to a `deploy` account whose key can only run the forced command `deploy-frontend <name> <tag>`, with name `stage` or `sworld`. On the server, that command pulls the image and starts it with one Compose file shared by all storefronts (`/etc/sworld/storefront-compose.yaml`) in the site's directory (stage: `/www/cartzilla.sigalev.ru`), as the `sworld` user's UID and GID. Both live in the Ansible role on `main` (`deploy/ansible/roles/server/`: `templates/deploy-frontend.j2`, `files/docker-compose.yaml`, sites and ports in `server_frontend_sites` in `defaults/main.yml`), so this repo has no Compose file.
- In the container, `container-entrypoint.sh` drops root with `setpriv` to `STOREFRONT_UID`/`STOREFRONT_GID` (or `node` without them), after giving that user `.next/cache` and `.next/server/route-cache`, where Next writes its caches and regenerated pages. Then `startup.sh` stops if it can't read `.env.local` or if any directory in the `.docker/` volume isn't writable, copies `.next/static` and `public/` over the previous build's files there (so `public/unavailable.html` never disappears), deletes what the new build lacks, and execs `node server.js` so `docker stop` reaches Next. `src/instrumentation.ts` names the process `nextjs-<STOREFRONT_PROCESS_NAME>`.
- nginx serves `.docker/static` and `.docker/public`, and answers 502–504 with `.docker/public/unavailable.html` as a 503. Its whole configuration is in the Ansible role on `main` (`roles/server/files/nginx/`); change it there, not on the server. Keep the five storefronts' `unavailable.html` alike apart from their branding.
- Product stock and reviews are lazy chunks loaded with `lazyWithReload` (`lib/lazy.ts`): after a deploy removes the old chunk, the page reloads once (at most once a minute) instead of failing.
- The other storefronts' branches have the same workflow without the tests and stage. `main` holds a stub of it, which GitHub needs to show the Run workflow button.
- "Frontend deployment" in `deploy/README.md` on the `main` branch documents the server side and the GitHub settings. That file also covers the rest of the server setup: nginx, Postgres, the Django backend (uWSGI, Celery), backups and monitoring. The Ansible playbook in `deploy/ansible/` sets most of it up. Don't infer the live server state from old notes; check there.

## Known follow-ups and deliberate limits

- Cookie-rename cleanup, **not before 2026-12-07** (four weeks after the switch to `__Host-` cookie names), and only after checking when it was deployed: remove `'csrftoken'` from `CSRF_COOKIES` in all five storefronts' proxies, together with Django's `CookieRenameMiddleware`, the `'sessionid'` fallback, their tests and comments. The checklist is in `PROBLEMS.md` (gitignored, may be missing in another clone). Whether Django's POST-only logout is deployed was still open there; check rather than assume.
- Account behavior the owner chose, don't change it in passing: registration and phone changes are confirmed by SMS in two steps; accounts created silently at checkout, preorder and warranty stay unverified; passwords need 8 characters and no complexity rules; wrong-password limits never block an SMS login; a taken email is disclosed only with a correct SMS code (except in the signed-in profile); our own order mail waits up to seven days for a confirmed email, and staff edits count as confirmed.
- Gaps left open on purpose (listed in `PROBLEMS.md`): no API path allowlist or captcha; some phone and username enumeration remains; receipts, delivery and analytics may get unconfirmed emails; abandoned-basket links point to sewing-world.ru; no full CSP, only `frame-ancestors` (Metrika's domains everywhere, `DENY` on auth and account pages); legacy accounts sharing a phone are merged by staff.
- The category filter/order SQL for the `cost` filter was left to the owner after the frontend deploy, and it isn't known whether it ran; don't run it as routine setup. The backend still lists both `price` and `cost` search facets until that cleanup.
- A Firefox tab once didn't apply CSS hot updates although the server sent them (older Next); reproduce on current versions before changing code. Tailwind keeps every class it has seen until a restart, and an error page reloads on every update, so probe with fresh classes on a healthy page.
