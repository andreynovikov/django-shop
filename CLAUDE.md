# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Django 6.1 backend for the "Швейный Мир" (sewing-world.ru) family of e-commerce sites. Verbose names and UI strings are in Russian, code comments are in English. The backend is on `main` only. The storefronts are Next.js apps that talk to the REST API here and get cache-revalidated through `shop/revalidation.py` (see below).

Every other branch of this repository is a storefront (see Commands), never a copy of the backend, so backend changes are not merged into them. The backend is deployed from `main` by hand, see deploy/README.md. When handing over a backend change, list the deploy steps it needs (migrate, collectstatic, uWSGI/Celery reload, an Ansible tag).

`AGENTS.md` carries the same guidance for Codex. When a rule here changes, change it there too.

The repository is public. `SERVER.md`, `PROBLEMS.md` and `server_inspection.txt` are gitignored notes on production and its open weaknesses: read them for infrastructure details, but never commit them or quote their findings.

## Commands

Project tests are in `tests/`. The `errors` and `filemanager` apps come from PyPI with their own tests, which the CI runs too. `.github/workflows/tests.yml` runs flake8 and the suites on every push, against a PostgreSQL 16 service container (production's major version). The frontends are branches of this repository (`sworld`, `family`, `janome`, `singer`, `dortak`), each with its own `.github/workflows/frontend.yml`. The copy on `main` is a stub that only fails, kept so GitHub shows the "Run workflow" button that deploys a frontend. A deploy logs in over ssh as `deploy`, whose key can only run the forced command `deploy-frontend <name> <tag>` (`deploy/ansible/roles/server/templates/deploy-frontend.j2`). That command pulls `ghcr.io/andreynovikov/<branch>:<tag>` and starts it with the shared Compose file (`roles/server/files/docker-compose.yaml`, installed as `/etc/sworld/storefront-compose.yaml`) in the site's directory, as the `sworld` user's UID and GID. Storefronts, their directories and ports are listed in `server_frontend_sites` (`roles/server/defaults/main.yml`); `stage` is the `sworld` branch at `/www/cartzilla.sigalev.ru`. "Frontend deployment" in deploy/README.md describes them.

Dependencies are managed with uv. `pyproject.toml` lists only the packages the code uses directly, plus flake8 in the `dev` group, and `uv.lock` pins everything. Add packages with `uv add` and upgrade with `uv lock --upgrade-package <name>`. `override-dependencies` lifts the `Django<6.1` that django-celery-beat and django-prometheus declare. Servers keep their virtualenv in `.venv/`, see deploy/README.md.

```bash
uv sync && source .venv/bin/activate    # or prefix the commands below with `uv run`
git ls-files -z '*.py' | xargs -0 flake8  # lint tracked files only, a bare flake8 walks local clones too; E501 is ignored, see .flake8
python manage.py check
python manage.py test tests errors filemanager --settings=tests.settings   # needs a Postgres role with CREATEDB, see tests/settings.py
python manage.py runserver
python manage.py makemigrations <app>
celery -A sewingworld worker -Q default,priority,integrations,import,revalidation
celery -A sewingworld beat              # schedules are stored in the DB (django_celery_beat)
python manage.py rerun_task <task_id>   # re-run a stored Celery task result
python manage.py cleanup_legacy_phones  # repair or remove accounts whose phone is not +7; reports only, --apply changes
python manage.py backup_db --dry-run    # hourly pg_dump into restic; --kind full|hot|config forces a kind
python manage.py postman_spec /tmp/spec.json  # OpenAPI spec of the Postman collection, see postman/README.md
```

Running anything requires:
- A `.env` in the repo root (read by `django-environ`). Required keys include `SECRET_KEY`, `DATABASE_URL` (PostgreSQL), `CACHE_URL` (memcached), `ALLOWED_HOSTS`, `ALLOWED_ORIGINS`, `ROOT_URLCONF`, `CELERY_BROKER_URL` (Redis), `ADMINS` (`name:email,...`), `LOGIN_URL`/`LOGIN_REDIRECT_URL`/`LOGOUT_URL`, `DEFAULT_FROM_EMAIL`, `SERVER_EMAIL`, `CSRF_COOKIE_SAMESITE`, `SESSION_COOKIE_SAMESITE`.
- `sewingworld/settings/integrations.py`. It is gitignored because it holds marketplace and payment credentials, but `settings/__init__.py` imports it unconditionally.
- A `logs/` directory, which the file log handlers write to.

## Architecture

### Settings and the two deployment modes
`DJANGO_SETTINGS_MODULE=sewingworld.settings`. That is a package: `__init__.py` reads env vars and then star-imports the topic modules (`apps`, `celery`, `constance`, `middleware`, `shop`, `integrations`, `logging`, ...). Add new settings to the matching topic module.

The `ADMIN=True` env var switches the process into **admin-site mode**. It also loads `.env.admin` on top of `.env`, and `sewingworld/urls.py` then serves only the 2FA-protected Django admin (`two_factor`, `massadmin`, `loginas`). Otherwise the process serves the public REST API at `/api/v0/` plus a few payment and document endpoints. The admin and the API run as separate uWSGI apps from the same code.

### Multi-site
Uses `django.contrib.sites` plus `sewingworld.models.SiteProfile` (root category, wholesale flag, order prefix, YooKassa credentials, Next.js revalidation token, domain aliases). For API requests, `FrontendKeyMiddleware` sets `request.site` from the storefront's `X-Frontend-Key` (`SiteProfile.frontend_key`) and `REMOTE_ADDR` from its `X-Real-IP`. Without a valid key it uses the default site, ignores the session cookie and lets only token holders change data; elsewhere `SiteDetectionMiddleware` sets it from the `Origin`/`Referer` header, matching against `Site.domain` or `SiteProfile.aliases`. API code should use `request.site` and not `SITE_ID`. `SITE_ID` is the main site (1, www.sewing-world.ru), whose orders in progress always hold stock, see `Product.get_stocks()`.

`CookieRenameMiddleware` moves visitors to new session and CSRF cookie names (`SESSION_COOKIE_NAME`/`CSRF_COOKIE_NAME` from `.env`, see `settings/__init__.py`). It and the legacy `sessionid` fallback stay until at least 2026-12-07 and until all five storefront proxies read the new CSRF cookie name; the date alone doesn't prove the switch happened. `SecurityMiddleware` adds nosniff, Referrer-Policy and COOP headers. HSTS and the HTTPS redirect come from nginx, so `SECURE_SSL_REDIRECT` stays off.

### Apps
- `sewingworld/`: project package and also an app. It holds the REST API (views in `api/`, serializers in `serializers/`, both bundled as catalog, shopping, orders, users, content and integrations, with shared pieces in `common.py`, where `NonNullModelSerializer` leaves out null, empty-string and empty-list fields, so storefront types treat them as optional; a DRF router in `urls.py`), the product list's filters and facets (`filters.py`), the custom admin site (`admin.py`, `SWAdminSite`), SMS gateways (`sms.py`, `smsru.py`, `sms_uslugi.py`; the provider is chosen through constance), and middleware.
- `shop/`: core domain. Models are split into `shop/models/*.py`, a module per model together with the models that only serve it (`Product` and `ProductImage`), and re-exported through `__all__` in `shop/models/__init__.py`, so a new model module has to be added there. Admin is split the same way in `shop/admin/`. The order admin keeps its business logic in `order_supply.py` (stock for suppliers), `order_shipping.py` (boxes, delivery, labels, acts, 1C export) and `order_editing.py`, and its list filters in `order_filters.py`. `AUTH_USER_MODEL = 'shop.ShopUser'`.
- `shop/tasks/`: Celery tasks in bundles: `user_interaction` (SMS and mail to customers), `admin` (notices to staff), `workflow` (order updates, storefront revalidation, basket expiry), `stocks` (stock and price import from 1C through Yandex Disk) and `integrations` (bonuses from 1C, retired with the bonus program although the code remains; currency rates, ModulPOS, Yandex Metrika). Each task is named `shop.tasks.<function>` explicitly, the name it had in the former `shop/tasks.py`, because beat schedules in the DB, stored results and queued tasks refer to it. Name new tasks the same way.
- Users: the API accepts +7 phones only (`PhoneValidator`). Registration and moving to another phone need a code sent to that phone (`PhoneCode`); accounts made silently at checkout keep `phone_verified=False` until an SMS login. Customer mail goes only to a confirmed address (`email_verified`, set by the link in `shop/email_confirmation.py` or by staff), and order mail waits for it (`confirmed_email` and `postpone_mail` in `shop/tasks/user_interaction.py`).
- Marketplace and payment integrations, each with `tasks.py` and usually `signals.py`: `beru` (Yandex Market), `ozon`, `wb` (Wildberries), `sber` (SberMegaMarket), `yandex_kassa` (YooKassa), `yandex_delivery`, `rarus` (bonus program). `unisender` and `mptt_urls` are plain helper modules, not installed apps.
- `errors`: server errors grouped for the admin only, the PyPI package `django-server-errors` (github.com/andreynovikov/django-server-errors, like `reviews` from `django-rated-reviews`). Changes to it go to that repository and come here as a release, with `uv lock --upgrade-package django-server-errors`. `ErrorCaptureMiddleware` (first in `MIDDLEWARE`) records every 5xx response, and a `task_failure` receiver records Celery tasks that fail for good. Repeats of an exception from the same view or task and the same project function count into one `Error`, which keeps its latest traces with masked locals. Mark functions that hold secrets with `@sensitive_variables()`, which also masks the frames they call.
- `filemanager`: the admin's file browser for the files that HTML text links to (`MEDIA_ROOT`, in place of FTP), the PyPI package `django-admin-filemanager` (github.com/andreynovikov/django-admin-filemanager), released like `errors`. Replacing a file keeps its URL, the `upload_to` folders of file fields are read-only through `FILEMANAGER_PROTECTED` (`sewingworld/settings/admin.py`), so a new `upload_to` folder belongs there, and "where used" searches the `TextField`s of the admin's models. Its `HTMLTextarea` widget (autosized, with an "Insert file" button that inserts `<img>`, `<video>` or `<a>`) goes on exactly the fields that the storefronts render with `dangerouslySetInnerHTML`. `tests/test_html_fields.py` lists them, so a field newly rendered as HTML belongs there and in its admin form. The admin forms clean that HTML with `shop.tidy.tidy_html5` (`shop/admin/forms.py`), not the model's `save()` or the storefronts.
- `blog/`, `forum/`: content apps. `forum` models are `managed = False` and map onto legacy tables, so they have no migrations.

### Product filters and facets
`ProductFilterSet` in `sewingworld/filters.py` declares every parameter of the product list; any other is ignored, so a new one has to be declared there. The storefronts send those in `productSearchParams` (`src/lib/search-params.ts`), ranges as `price=a-b`. `price` is the list price column. `cost` is the price that the site shows, discounts taken off: the `cost=a-b` filter, its facet and `ordering=cost` work over `Product.with_site_cost()`, the SQL twin of `Product.site_cost()`, so a change to one has to go to the other. `Category.filters` names the filters a category page shows. `CategorySerializer` describes them, and the product list of that category brings their choices and ranges as `filters`, counted over the products that the other parameters find. A full-text search brings `manufacturer`, `price` and `cost` the same way. The storefronts pick a control by `class`, or by `widget` for the sliders (`ShopRangeWidget`, `ShopSliderWidget`). These names come from Django forms that are no longer used, but keep them.

### Integrations pattern
`shop.models.Integration` is keyed by `(target_site, utm_source)`. The target storefront scopes the API and storefront checkout attribution. `source_site` identifies the sales channel and supplies feed pricing and marketplace order sites. Its per-channel config lives in the `settings` JSONField (for example `ym_campaign` or `warehouse_id`), and `ProductIntegration` stores per-channel price and a `notify_stock` flag. Integration apps hook `post_save` on `Product`/`Order` and queue Celery tasks to push stock and order status. Orders from channels with `uses_api=True` skip the normal customer-notification flow in `shop/signals.py`.

### Side effects through signals and Celery
Order status changes are watched with `django-model-utils` `FieldTracker` (`order.tracker.has_changed('status')`), and the `post_save` receivers in `shop/signals.py` and each integration's `signals.py` dispatch SMS, email, manager notifications, POS sync and storefront revalidation as Celery tasks. Saving a model can therefore queue background work. Setting `product.num = -1` is the convention for "stock needs to be re-reported". Reading `product.instock` then counts it and saves only `num`. `import1c` resets it for every product it imports and queues `count_stocks`, which counts them in the worker so that API requests don't have to.

### Storefront revalidation
The storefronts' pages are static. Each storefront tags the API requests its pages make with the data they ask for (`category:<id>`, `product:<code>`, `catalog`, …; the list is in `shop/revalidation.py` and the storefronts' `lib/queries/cache-tags.ts`, keep them in step), and renders again the pages whose tags it receives at `/api/revalidate`.
- `shop/revalidation.py` turns a change into the tags it touches: `revalidate(tags, sites)`, `revalidate_products(ids)` (the product's page, its categories' lists, its sales actions, the home page, products that show it as an accessory or a set part), `revalidate_product_pages(ids)` and `revalidate_stock({id: stock before})`, which counts the stock at commit and takes only the products whose stock shows otherwise.
- Changes are collected per transaction and sent once it commits, one batch of tags per site through the `revalidate_nextjs` task. Outside a transaction they are sent at once, so code that changes many products collects their ids and calls `revalidate_products()` once (as `import1c` does through `post_update_products` and `count_stocks`).
- Edits and price changes expire the tags at once; stock goes in the background (stale-while-revalidate, `background` in the payload).
- The receivers are in `shop/signals.py`; `REMEMBERED` there keeps the fields whose old values matter (an old slug, url or place). The product admin calls `revalidate_products()` in `save_model()`, the 1C import compares the prices and stock before and after. A new model shown on a storefront's static page needs a receiver here and a tag on the storefront's request.

Tasks are routed to named queues (`priority`, `integrations`, `import`, `revalidation`, `default`) and most use `autoretry_for`/`retry_backoff`. Results go to the DB (`django_celery_results`). The `PRIORITY_*` constants in `sewingworld/tasks.py` are currently `None`, so priorities are effectively disabled. Runtime-editable settings such as the default seller or SMS provider live in `django-constance` (`sewingworld/settings/constance.py`).

### Query counts
API time goes mostly to Python, and grows with the number of queries per request. Product serializers have a `prefetch()` classmethod that adds the `only()` columns and the prefetches they need (a product row has about 150 columns), so pass a queryset through it before serializing products. `Product.site_price_record()` reads prefetched `site_prices`. `Product.get_stocks()` counts the stock of many products in a few queries, and `get_stock()` is it for one: the integrations' feeds and the stock updates sent to marketplaces count their whole list at once. `DISTINCT` over product rows is costly, so filters through many-to-many relations (`in_category`, `kind`) use a subquery instead of a join, and `ProductViewSet` orders ties by `pk`. Tests check that query counts don't grow with the objects shown (`count_queries` in `tests/clients.py`).

### Backups
`sewingworld/management/commands/backup_db.py` runs hourly from a systemd timer and streams `pg_dump` into a restic repository (`RESTIC_*` in `.env`) on an append-only rest-server. It makes a full dump daily and after migrations, and otherwise a hot dump of the `DB_BACKUP['HOT_MODELS']` rows only (`sewingworld/settings/backup.py`). Full runs also save `.env` and `integrations.py`. The backup host runs `deploy/backup/maintain.sh` (retention, alarms, weekly restore test), and `deploy/backup/restore.sh` lays the latest hot dump over its full dump. A new model whose rows change often belongs in `HOT_MODELS`. A table of logs belongs in `EXCLUDE_DATA_APPS`. deploy/README.md has the setup and the restore runbook.

### Infrastructure
PostgreSQL (the DB backend is wrapped by `django_prometheus`, and the code relies on Postgres features: `ArrayField`, JSON lookups, FTS), memcached, Redis as the Celery broker, and uWSGI behind nginx. PostgreSQL is a DBaaS on another host; `DATABASES` sets `lock_timeout=5s` per connection, which `backup_db` passes to pg_dump as `PGOPTIONS`. `deploy/README.md` describes the server (Debian, systemd units for uWSGI and Celery, the per-site `/www/<domain>` layout), and the Ansible playbook `deploy/ansible/site.yml` (roles `server` and `backup_host`, runbook in `deploy/ansible/README.md`) sets it up: packages, users, sshd with OTP, nftables, uWSGI and Celery units (the apps, with processes and threads, in `roles/server/defaults/main.yml`), certbot's reload hook, backups, log rotation, a daily `docker-prune.timer` and the storefront deployment. The whole nginx configuration is in `roles/server/files/nginx/`: `nginx.conf`, every site, `sw_proxy_params` and snippets. The `nginx` tag installs it, enables `server_nginx_sites_enabled` and runs `nginx -t` before reloading, so nginx changes are made there and not on the server. Storefront proxies answer 502–504 with the storefront's own `.docker/public/unavailable.html` as a 503. TLS files, `/etc/nginx/htpasswd`, OTP secrets, the backend checkout with its `.env` and the storefronts' feed templates stay manual. Site logs go to `/var/log/nginx`, never into `/www`. The 1C stock import reads from `SHOP_IMPORT_DIRECTORY` (`/www/www.sewing-world.ru/import`).
